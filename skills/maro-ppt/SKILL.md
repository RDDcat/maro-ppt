# 몸값 올리는 PPT 제작

발표 덱 하나를 **인터뷰 → 확장 → 생성 → 수정** 순서로 만든다.

핵심은 **확장**이다. 사용자가 준 항목을 슬라이드로 1:1 옮기지 않는다.
각 항목이 청중을 어디까지 데려가야 하는지 판단해서, 그만큼의 장으로 펼친다.

> 디자인 규격 전문: `references/design-spec.md`
> 새 덱의 시작점: `template.html` (자립형 단일 HTML, 외부 요청 0건)

---

## 1. 인터뷰 — 한 번에 하나씩 묻는다

**질문을 한꺼번에 쏟지 않는다.** 앞의 답이 뒤의 질문을 바꾸기 때문이다.
사용자가 첫 요청에서 이미 준 항목은 건너뛰고, 확인만 한 줄로 한다.

### 1단계 — 핵심 메시지

> "이 발표를 듣고 난 사람이 딱 한 문장만 기억한다면, 그게 뭐였으면 좋겠어요?"

**주제가 아니라 주장이어야 한다.** 판정법: 반대 문장을 만들어 본다.

| 답 | 반대 문장 | 판정 |
|---|---|---|
| "토큰에 대해서" | (반대가 없음) | ✗ 주제다. 다시 묻는다 |
| "토큰을 모르면 API 비용이 10배로 샌다" | "토큰을 몰라도 비용은 안 샌다" | ✓ 주장이다 |

주제로 답하면 되묻지 말고 **후보 2~3개를 만들어 고르게 한다.** 물어보기만 하면 같은 답이 온다.

핵심 메시지는 덱 전체의 척추다. 뒤의 모든 판단이 여기에 걸린다.

### 2단계 — 후킹 제목

> "표지에 걸 제목이 있나요? 없으면 제가 세 개 뽑아 드릴게요."

**후킹은 표지 한 장에서만 한다.** 본문 슬라이드 제목은 후킹하지 않는다(3-④).
장마다 후킹을 걸면 장끼리 경쟁해서 덱 전체가 난잡해진다.

없다고 하면 핵심 메시지에서 **서로 다른 방식으로 세 개**를 만들어 보인다.

| 방식 | 예 |
|---|---|
| 손실 | 모르면 새는 돈, 토큰 |
| 숫자 | 같은 질문, 비용은 10배 |
| 오해 | 토큰은 글자 수가 아니다 |

- 표지 부제(`p.body`)는 **핵심 메시지를 그대로 또는 한 겹 압축해서** 쓴다.
- 마무리 장의 결론 밴드에 핵심 메시지를 **다시 한 번 문장 그대로** 놓는다. 표지와 수미상관이 된다.

### 3단계 — 슬라이드 구성

> "다룰 항목을 순서대로 적어 주세요. 한 줄씩, 거칠어도 됩니다."
> "적어 주신 항목이 슬라이드 한 장씩이 되는 건 아니고, 각 항목을 설득 구조로 펼쳐서 만들 거예요."

**미리 알린다.** 알리지 않으면 생성 결과를 보고 "내가 말한 것과 다르다"가 된다.

- 항목이 **2개 이하**면: 다룰 범위가 좁다. 무엇을 더 넣을지 되묻거나, 짧은 덱(6~8장)으로 가겠다고 말한다.
- 항목이 **12개 초과**면: 주제를 둘로 쪼개자고 제안한다. 한 덱에 다 넣으면 어느 것도 안 남는다.

### 4단계 — 나머지 (한 번에 묻는다)

| 항목 | 기본값 |
|---|---|
| 듣는 사람 | 비개발자 |
| 저장 위치·파일명 | 현재 작업 디렉터리 / `{후킹 제목}.html` |
| 헤더 좌상단 라벨(BRAND) | 주제의 영문 대문자 한 단어 |
| 스크린샷·수치 자료 | 없음 (없으면 증거 유형 장을 빼고 짧게 간다) |

장수는 **묻지 않는다.** 내용이 정한다(2-3).

## 2. 확장 — 항목을 설득 구조로 펼친다

이 절이 이 스킬의 핵심이다. HTML을 열기 전에 머릿속에서 끝낸다.

### 2-1. 항목의 유형을 먼저 판별한다

사용자가 준 한 줄이 **무엇을 하려는 문장인지** 정한다. 유형이 사이클을 정한다.

| 사용자가 쓴 말 | 유형 |
|---|---|
| "X의 정의", "X란 무엇인가", "X 설명" | **개념** |
| "A와 B의 차이", "A vs B", "헷갈리는 것" | **대조** |
| "어떻게 쓰는가", "사용법", "세팅" | **절차** |
| "왜 필요한가", "효과", "근거" | **근거** |
| "무슨 도구", "추천 툴" | **도구** |
| "사례", "우리가 해 본 것", "실제로" | **사례** |
| "정리", "다음 할 일", "마무리" | **전환** |

### 2-2. 유형별 설득 사이클

각 칸이 슬라이드 후보다. **모든 칸을 채우지 않는다.** 청중이 이미 아는 칸은 뺀다.

| 유형 | 사이클 (→ 순서대로) |
|---|---|
| **개념** | 왜 알아야 하나(겪는 불편) → 정의 한 문장 → 실물 예시 → 경계(이건 아니다) |
| **대조** | 겉보기엔 같다 → 갈라지는 지점 하나 → 어느 쪽을 고르나(기준) |
| **절차** | 준비물 → 단계 3개 → 그대로 칠 프롬프트 → 결과 |
| **근거** | 주장 → 숫자·화면 증거 → 나올 만한 반론 하나 처리 |
| **도구** | 문제에 필요한 조건 → 도구와 출처 링크 → 고르는 기준 |
| **사례** | before(문제 상태) → 무엇을 바꿨나 → after(숫자) |
| **전환** | 여기까지의 요약 → 오늘 할 수 있는 첫 걸음 → 별도로 고민할 것 |

> 예 — 사용자 입력 `토큰의 정의를 설명`
>
> | 장 | 유형 칸 | 제목 | 도해 |
> |---|---|---|---|
> | 1 | 왜 알아야 하나 | 같은 질문에 다른 요금 | `.stat` 숫자 대비 |
> | 2 | 정의 | 토큰은 모델이 읽는 조각 | `.flow` 문장→조각→숫자 |
> | 3 | 실물 예시 | 한국어와 영어의 토큰 수 | `.duo` 2열 비교 |
>
> "경계" 칸은 뺐다. 비개발자 청중에게 "토큰이 아닌 것"은 아직 필요 없다.

### 2-3. 장수는 내용이 정한다

한 장에 담는 단위는 **메시지 하나**다. 청중이 "그래서?"를 한 번만 물으면 되는 크기.

**쪼개는 신호** — 하나라도 걸리면 두 장으로 나눈다.

- 도해가 두 개 필요하다
- 리드 문장(`p.body`)이 두 문장이 된다
- 나열 항목이 6개를 넘는다
- 정의와 예시를 같은 화면에서 봐야 한다
- 숫자와 그 숫자의 해설을 같이 봐야 한다

**합치거나 빼는 신호** — 하나라도 걸리면 앞 장에 흡수하거나 지운다.

- 도해 없이 한 줄로 끝난다
- 앞 장의 결론 밴드와 같은 말을 한다
- 그 장을 빼도 논리가 이어진다
- 사용자가 시킨 항목이라 넣었을 뿐, 핵심 메시지 쪽으로 한 칸도 못 올라간다

**전체 분량**: 9~15장이 정상이다. 20장을 넘으면 주제를 쪼갠다.
6장 미만이면 각 항목의 사이클에서 뺀 칸을 다시 본다.

### 2-4. 덱 전체의 뼈대

사용자가 말하지 않아도 **표지·도입·마무리는 스킬이 넣는다.**

```
01  표지        후킹 제목 + 핵심 메시지(부제)
02  도입        듣는 사람이 아는 불편을 재현 — 첫 항목의 "왜" 칸이 여기 온다
03~n  본론      항목별 설득 사이클을 순서대로
n+1 마무리      할 수 있는 것 / 별도로 고민할 것 2카드 + 핵심 메시지 밴드
```

- 목차 장은 **12장을 넘을 때만** 넣는다. 짧은 덱에서는 흐름을 끊는다.
- 본론에서 유형이 바뀌는 지점(개념 → 절차 등)은 앞 장의 결론 밴드로 잇는다. 따로 전환 장을 만들지 않는다.

### 2-5. 확장 결과를 스스로 점검한다 (생성 직전)

**핵심 메시지 사다리.** 각 장의 결론 한 줄을 세로로 적어 본다.
위에서 아래로 읽었을 때 핵심 메시지에 한 칸씩 가까워져야 한다.
제자리걸음인 장은 뺀다. 이 점검을 거른 덱은 장은 많은데 남는 게 없다.

```
□ 각 장이 메시지 하나만 말하는가
□ 결론 한 줄을 이어 읽으면 핵심 메시지로 수렴하는가
□ 후킹이 표지 한 장에만 있는가
□ 사용자가 준 항목이 전부 어딘가에 반영됐는가 (뺐다면 왜 뺐는지 말할 수 있는가)
□ 같은 도해 유형이 세 번 연속 나오지 않는가
```

### 2-6. 레이아웃 고르기

| 그 장이 하려는 것 | `<section class="…">` |
|---|---|
| 글과 그림이 짝을 이룬다 (정의+흐름, 비교, 절차) | `slide two dense` |
| 도해가 넓게 펼쳐져야 한다 (3열 카드, 벤, 숫자 히어로, 스크린샷) | `slide one` |
| 표지 | `slide title` |

## 3. 절대 어기지 않는 것

이것만 지키면 이 덱처럼 보인다.

```css
--paper:#f4f1e9;   /* ① 배경은 흰색이 아니라 아이보리 */
--ink:#17231d;     /* ② 검정이 아니라 짙은 초록빛 잉크 */
--lime:#c9f450;    /* ③ 강조색은 이 하나뿐 */
```

**④ 본문 제목은 그 장의 내용을 그대로 쓴다. 후킹은 표지에서 이미 했다.**

```html
<h1>MCP 서버의 <span class="accent">세 가지 구성요소</span></h1>
<h1>API 방식의 <span class="accent">한계</span></h1>
<h2>연결 비용 <span class="accent">N×M vs N+M</span></h2>
```

- **한 줄, 명사구가 기본이다.** 그 장에서 다루는 것을 이름으로 부른다.
- **본문에서 쓰지 않는 것**: 반문("왜 자꾸 헷갈릴까?"), 반전("질문이 틀렸다"),
  조건+주장 2단 구성, 감탄·과장. 주장은 제목이 아니라 **리드 한 문장과 결론 밴드**가 한다.
- **예외는 표지 한 장뿐이다.** 표지 `h1` 에는 인터뷰 2단계에서 받은 후킹 제목을 그대로 건다.
- 형광펜 `.accent` 는 제목의 **핵심 명사**에 건다. `linear-gradient(transparent 64%,var(--lime) 64%)`.
  **한 장에 한 번만.** 두 번 쓰면 강조가 사라진다 — 이쪽이 진짜 규칙이다.
- `<br>` 로 직접 끊은 줄에만 `.nowrap` 을 붙인다. 한 줄 제목에는 필요 없다.
- 제목 자간 `-.048em` 을 건드리지 않는다.

**⑤ 구조는 각지고, 예시 UI만 둥글다.**

| 대상 | radius | 색 |
|---|---|---|
| 카드·밴드·프레임·프롬프트 | **0** | 흰 면 + `1px var(--line)` |
| 슬라이드 안에 그린 "제품 버튼·진행 막대" | 6~12px / 999px | `--blue` |

파랑·라운드·알약은 *덱의 스타일이 아니라 인용된 제품의 스타일*이다. 덱 자신의 구조에 쓰지 않는다.

**⑥ 태그를 쓰지 않는다.** `.chip` / `.chips` 는 폐기됐다.
주제를 태그로 나열하면 관계가 안 보이고 단어만 훑게 된다.

## 4. 도해 고르는 법

무엇을 놓을지는 **말하려는 관계**로 정한다. 예쁜 것으로 정하지 않는다.

| 말하려는 것 | 쓰는 것 | 클래스 |
|---|---|---|
| 순서·인과 | 화살표 흐름 3칸 (마지막 칸만 잉크) | `.flow` |
| A와 B의 차이 | 2열 카드 + 아래 잉크 펀치라인 | `.duo` + `.band.full` |
| 구성요소 셋 | 상단 5px 잉크 바 카드 3개 | `.trio` + `.card.top` |
| 절차 | 원형 번호 목록 | `.steps` |
| 두 집합의 관계 | 겹치는 원 두 개 (교집합만 라임) | `.venn` |
| 수치 대비 | 큰 숫자 두 개 (전은 회색, 후는 형광펜) | `.stat` |
| 그대로 칠 프롬프트 | 어두운 모노 블록 + 라임 레일 | `.prompt` |
| 화면 증거 | 검은 프레임 + 오프셋 그림자 | `.shot` / `.frame` |

**도해는 결론 밴드 한 줄로 닫는다.** 그림만 놓고 넘어가지 않는다.

```html
<div class="band">{결론 문장}<b>{숫자}</b></div>   <!-- 잉크: 성과·결론 -->
<div class="band lime">{판단 기준 한 줄}</div>       <!-- 라임: 전제·비용·주의 -->
```

밴드는 덱 전체에서 **6개 이하**, 프롬프트 블록은 **2개 이하**로 쓴다. 남발하면 무게가 사라진다.

## 5. 생성

1. `template.html` 을 **4단계에서 정한 경로**로 복사한다.
2. `{중괄호}` 자리를 채운다. **필요 없는 `<section class="slide">` 은 통째로 지운다.** 헤더 분모는 스크립트가 자동으로 센다.
3. 템플릿에 없는 유형이 필요하면 `references/design-spec.md` 6-3 의 15장 골격에서 가져온다.
4. 7절 체크리스트를 돌린다.
5. `open "{파일}"` 로 열어 준다.
6. **장별 한 줄 요약 표를 함께 출력한다.** 사용자가 고칠 장을 손가락으로 짚을 수 있어야 한다.

   ```
   01 표지    모르면 새는 돈, 토큰
   02 도입    같은 질문에 다른 요금        .stat
   03 정의    토큰은 모델이 읽는 조각      .flow
   ...
   ```

7. "몇 번 장이 마음에 안 드는지 말해 주세요"로 닫는다. 수정은 그 장만 고친다.

---

## 6. 쓰기 규칙

- 본문 제목에 마침표를 찍지 않는다. 물음표도 쓰지 않는다(3-④).
- 리드 `.body` 는 **한 문장**. 두 문장을 넘기면 제목이 틀린 것이다.
- 담백한 한국어. 과장·감탄사·마케팅 문구 금지. (후킹은 표지에서 끝났다)
- 장식용 이모지 금지. `→ ↗ ✓ ① 01` 같은 기능 기호만.
- 외부 링크는 `이름 ↗` 형태의 텍스트 링크로.
- 한 장에 항목 6개 이상이면 두 장으로 나눈다.

## 7. 완료 전 체크

```
□ 배경이 #f4f1e9 인가 (흰색이 아닌가)
□ 후킹이 표지 한 장에만 있고, 본문 제목은 명사구인가
□ 제목마다 .accent 가 한 번씩만 걸렸는가
□ 직접 끊은 제목 줄이 .nowrap 으로 감싸였는가
□ 마무리 장에 핵심 메시지가 문장 그대로 놓였는가
□ 카드·밴드의 radius 가 0 인가
□ 태그(.chip / .chips)를 쓰지 않았는가
□ 라운드·파랑·알약이 예시 UI 안에만 있는가
□ 그림자가 스크린샷 프레임 외에 없는가
□ 각 도해가 결론 밴드로 닫히는가 (밴드 합계 6개 이하)
□ 프롬프트 블록이 2개 이하인가
□ 푸터에 [편집] 버튼과 편집 스크립트가 살아 있는가
□ --zoom 과 [ ] 배율 스크립트가 살아 있는가
□ 글자가 SVG <text> 가 아니라 편집 가능한 HTML 안에 있는가
□ 외부 요청 0건인가 (웹폰트·CDN·http 이미지 없음)
□ 900px·600px 로 줄여도 1단으로 접히는가
```

검증:

```bash
f="{만든 파일}"

grep -o '<text'                   "$f" | wc -l   # 0 이어야 정상 (SVG 글자 금지)
```

## 8. 인라인 편집 — 빼지 않는다

`template.html` 에는 **클릭해서 글자를 고치고 원본 파일에 덮어쓰는 기능**이 들어 있다.

| 동작 | 방법 |
|---|---|
| 편집 켜기/끄기 | 푸터 `[편집]` 또는 `E` (한글 입력 상태의 `ㄷ` 도 먹는다) |
| 고치기 | 글자를 클릭하고 그대로 타이핑 (서식·구조는 안 바뀐다) |
| **저장 = 덮어쓰기** | `[저장]` 또는 `⌘S` (한글 입력 상태의 `⌘ㄴ` 도 먹는다) — **처음 한 번만** 파일을 묻고, 그 뒤로는 묻지 않고 덮어쓴다 |
| 되돌리기 | `[원래대로]` |

- 파일 핸들은 IndexedDB 에 남아 **브라우저를 껐다 켜도 유지된다.**
- 편집 중에는 `←` `→` 로 장이 넘어가지 않는다(`e.target.isContentEditable` 로 막아 둠).

**덮어쓰기가 안 될 때** — File System Access API 가 없는 Safari·Firefox 이거나 `file://` 이면
자동으로 내려받기로 떨어지고 푸터에 이유가 뜬다. 로컬 서버로 열면 정상 동작한다.

```bash
cd "{덱이 있는 폴더}" && python3 -m http.server 8000
# → http://localhost:8000/{파일}.html 을 Chrome 계열에서 열고 저장
```

**덱을 만들 때 지킬 것**

- 글자는 반드시 편집 대상 선택자 안에 두어야 한다:
  `h1 h2 h3 p small figcaption .link .band .flow span .flow strong .steps>div .pairs>div .breakdown span .stat .prompt`
- **SVG 안에 `<text>` 로 글자를 넣지 않는다.** SVG는 도형만, 글자는 그 위에 얹는 HTML(`position:absolute`)로. `.venn` 이 그 방식이다.
- 편집기는 서식이 아니라 **글자만** 바꾼다(`plaintext-only`).

## 9. 강의 중 화면 배율 — `[` `]`

강의실 뒷자리에서 글씨가 작을 때 키보드로 슬라이드를 키우고 줄인다. 버튼도 표시도 없다.

| 키 | 동작 |
|---|---|
| `]` | 5%씩 확대 (최대 200%) |
| `[` | 5%씩 축소 (최소 50%) |
| `\` | 100% 로 되돌리기 (한글 입력 상태의 `₩` 도 먹는다) |

- 배율은 `:root` 의 `--zoom` 하나이고 `.slide` 에만 `transform:scale(var(--zoom,1))` 로 걸린다. 헤더·푸터는 제자리다.
- `.slide` 폭이 `min(1280px, calc(100% / var(--zoom,1)))` 이라 **확대해도 좌우로 잘리지 않는다.**
- 실제로 쓰는 범위는 **100~140%**. 그 이상은 도해가 많은 장에서 위아래가 잘린다.
- 슬라이드 밖(헤더·푸터)에 본문을 두지 않는다. 배율이 걸리는 것은 `.slide` 뿐이다.
- `@keyframes enter` 두 프레임에 `scale(var(--zoom,1))` 이 들어 있어야 한다. 빼면 장을 넘길 때마다 100%로 튄다.

## 11. 이미지 넣기

외부 요청 0건이 원칙이므로 스크린샷은 **base64 data URI 로 인라인**한다.

```bash
python3 - <<'PY'
import base64,pathlib
p=pathlib.Path("스크린샷.png")
print("data:image/png;base64,"+base64.b64encode(p.read_bytes()).decode())
PY
```

- 폭 1600px 이하로 줄여서 넣는다. 이미지 3장이면 파일이 1.2MB 가 된다.
- **before 이미지는 죽인다**: 감싸는 요소에 `class="fade"` (`opacity:.52; grayscale(.45)`).
  두 장을 나란히 놓고 한쪽을 흐리게 하는 것으로 "이쪽을 보라"를 말한다.

## 12. macOS 한글 파일명 주의

macOS 의 한글 파일명은 **NFD(자모 분리)** 로 저장된다.
`find -name "*발표*"` 처럼 **와일드카드 패턴에 한글을 넣으면 0건**이 나오고, 그게 에러가 아니라 통과처럼 보인다.

- 셸: `find "{폴더}" -name "*.html"` — 패턴에 한글을 넣지 않는다.
- 경로를 정확히 적는 것(`cat "{폴더}/파일.html"`)은 잘 된다.
